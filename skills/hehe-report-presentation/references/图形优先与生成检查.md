# 图形优先与生成检查

## 制作顺序

1. 读取定稿全文，找出本页或下拉模块中的主体、关系、数量、条件与解释，保留原文对应记录。
2. 按 [版式与组件选用.md](版式与组件选用.md) 选能表达主要关系的图式，写入页面源的 `visual_plan`，再排图文。下拉报告按主题模块处理，无需先做分页脚本。
3. 图形承载关系，完整文字解释事实、原因和条件。节点标题写清对象与动作；较长论述放在对应节点旁或图下，保持可见和可追读。
4. 用实际内容先做代表页，检查连线、顺序、分组与数值是否准确，完整解释是否可读，再扩展整稿。最后连看缩略图和原尺寸，处理同款版式反复出现、关系不清和文字缺失。

资金流用方向区分付款与交付，阶段图区分已完成与计划，条件图写明分支依据，数量图保留单位和口径。材料没有数量仍可画定性结构；没有依据的比例、因果和交易关系不能补画。精确查阅、同维度文字比较用表格；无独立图形关系的连续论证保留正文。选择随内容变化，不规定图形占比。

## 页面源中的内部方案

每个 `kind: content` 页面或模块填写一个 `visual_plan`；一个模块内含多个独立图式时用对象列表。封面、目录、章节页和封底不填。方案不显示在对客页面。

```json
"visual_plan": {
  "relation": "flow",
  "message": "机器人公司向采集服务商支付采集费，服务商交付数据，模型团队反馈验收结果。",
  "form": "network",
  "target": "payment-data-flow",
  "explanation": "各主体旁保留职责说明，图下保留验收与收费条件的完整段落。"
}
```

- `relation`：本页主要关系，取下表值。
- `message`：具体对象之间是什么关系，用完整句子说明。
- `form`：实际图式，取下表对应值。
- `target`：图文对象的唯一 HTML `id`；标准组件直接填写 `id`，项目专用 `body` 在相应根元素设置 `id`。
- `explanation`：完整论述在页面中的具体位置。
- `reason`：选择 `table` 或 `prose` 时必填，说明读者要查阅、比较或理解什么，以及该形式为何适合；“原文较长”“没有现成组件”不是理由。

| relation | 关系 | 可用 form |
|---|---|---|
| `flow` | 主体间付款、交付、数据或反馈 | `network`、`flow` |
| `sequence` | 先后阶段、时间与持续区间 | `flow`、`timeline`、`gantt` |
| `convergence` | 多分支共同汇入一个判断 | `branch_merge` |
| `decision` | 条件决定不同选择 | `decision` |
| `structure` | 层级、包含、上下游依赖 | `structure` |
| `change` | 起点、增减与最终结果 | `waterfall` |
| `comparison` | 对象间差异 | `bar`、`hbar`；逐项文字比较可用 `table` |
| `trend` | 时间趋势 | `line` |
| `composition` | 总量构成 | `stacked`；无比例数据时用 `structure` |
| `distribution` | 个体或分组分布 | `distribution` |
| `calculation` | 因子、运算与结果 | `calculation` |
| `coordination` | 阶段与角色、行为、困难的交叉关系 | `swimlane`、`journey` |
| `lookup` | 报价、资料或其他明细查阅 | `table` |
| `narrative` | 定义、条件与连续论证 | `prose` |

`briefing`、`split` 是排版容器。方案指向其中实际承担表达的图表；完整论证确为本页主体时，可以选择 `narrative/prose` 并解释理由。泳道和旅程矩阵适合交叉查看阶段与角色，不替代需要连线的资金网络或条件分支图。

## 对应实际对象

标准组件由生成器识别其实际结构；`analysis_path` 对应 `flow`。图表识别 `chart_type`，不用 `layout` 名称或“图表化”字样判断是否画了图。现成组件不支持时使用项目专用 SVG 或 HTML/CSS。

专用关系图的根元素填写 `data-visual="图式"`；可见节点以 `data-node` 命名，实际连线以 `data-from`、`data-to` 指向节点。以下是最小关系图结构，项目中需按内容安排尺寸及完整解释：

```html
<figure id="payment-data-flow" data-visual="network">
  <svg viewBox="0 0 600 160" role="img" aria-label="机器人公司支付采集费，采集服务商交付数据">
    <g data-node="buyer"><rect x="10" y="50" width="180" height="60" fill="#edf4f6"/><text x="24" y="86">机器人公司</text></g>
    <g data-node="supplier"><rect x="410" y="50" width="180" height="60" fill="#edf4f6"/><text x="424" y="86">采集服务商</text></g>
    <path data-from="buyer" data-to="supplier" d="M190 65 H410 l-10 -5 m10 5 l-10 5" fill="none" stroke="#173f54"/>
    <text x="210" y="50">支付采集费</text>
    <path data-from="supplier" data-to="buyer" d="M410 100 H190 l10 -5 m-10 5 l10 5" fill="none" stroke="#208e91"/>
    <text x="210" y="130">交付数据</text>
  </svg>
  <figcaption>此处保留原稿中有关交付、验收与收费条件的完整解释。</figcaption>
</figure>
```

HTML/CSS 连线在实际可见箭头元素上另加 `data-connector="true"`。条件图的分支连线增加 `data-condition`，内容与页面可见条件标签相同。阶段轴可使用一条共同轴线，各可见阶段填写 `data-node` 和不同的 `data-order` 顺序值。专用数量图的根元素填 `data-unit`，实际柱、点或线填写 `data-value`；瀑布图按原始增减值标注，不能用像素位置代替数值。这些字段只记录已有图形对象，不另造数据或简化正文。

## 生成检查及兼容转换

`scripts/render_report.py` 对新设计的 JSON 页面源默认执行 `scripts/visual_plan.py`，在写出文件前检查：正文页是否有方案、关系与图式是否相符、目标是否唯一可见、相应图形对象是否存在。缺少方案、把流程写成表格、仅有空 SVG 或图标、连线指向不存在的节点，都停止生成并指出页面。

直接 Markdown 转下拉 HTML 保留原有基础阅读能力；历史 JSON 原样重渲染可用 `--preserve-layout`。这两条路径记录为 `preserved-layout`，不计为本轮图形优化。用户要求美化，或按本 Skill 制作新视觉报告时，必须完成图形方案并使用默认检查路径；Markdown 可直接按主题转为下拉 JSON，不依赖其他 Skill。PDF 和 PPT 从已检查的 HTML 导出。

脚本检查对象与方案的一致性；Agent 另对照原稿检查选图是否恰当、关系是否成立、完整内容是否保留，并实际查看图文大小、阅读顺序和整稿变化。记录具体页及发现，不能把“检查通过”写成“美观已获认可”。
